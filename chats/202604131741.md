如何让一个人长期、低压力地积累、管理、生成、评估和复用自己的 skills。

3. Skill Eval 评估

这是 Skill Notebook 里最有产品价值的模块之一。

因为写 skill 最怕的不是“写不出来”，而是：

tools 权限不合理

skill 能跑，但不稳定

所以 eval 是必须的。

它解决的问题

让 skill 从“像是一个 skill”变成“更可能是一个可用的 skill”。

V1 要支持什么

我建议 eval 先做四类检查：

1）完整性检查

name

description

arguments

tools

examples

references（可选）

2）清晰度检查

看文字是否足够明确：

任务目标是否清楚

输入是否清楚

输出是否清楚

边界是否清楚

有没有声明工具

prompt 是否可执行

清晰度

可执行性

示例质量

让 skill 像笔记一样被沉淀，像代码一样被版本化，像工具一样被复用。

2. 产品背景

过去一段时间，成熟的 skill 生态已经证明了一件事：
用户真实需要的，不只是“安装更多 skill”，而是围绕 skill 的完整工作流，包括：

用自然语言找到自己需要的 skill

把一段方法论、文章或工作流快速转成 skill

用评估判断 skill 是否真的有用

让对话和使用过程变成可复用资产

从 Git 直接安装 skill

在私有与公开之间做边界管理

这些能力在 42plugin 的公开产品演进里都能看到：它公开提到过自然语言搜索、42skill、42eval、对话自动保存/导入导出/全文检索、Git 直装、组织版私有共享，以及“你的插件不该被迫公开，换台电脑不该从头再来”。
活水插件
+1

但你的核心痛点不是“市场里有没有 skill”，而是：

我需要一个完全属于我自己的、本地的、可控的 skill 工作台。

你做 Skill Notebook 的直接原因也很清楚：
你曾经依赖公共 skill 平台，但遇到过 skill 被删、链接失效、历史资产丢失的问题。
这说明 个人能力资产不能完全托管在外部平台上。

因此，Skill Notebook 的产品起点不是 marketplace，而是：

个人本地版 Skill Hub 管理编辑器。

3. 产品目标

Skill Notebook 的目标不是做一个新的 42plugin，也不是做团队协作平台。
它只解决一个问题：

如何让一个人长期、低压力地积累、管理、创建、评估和检索自己的 skills。

核心目标

让 skill 成为个人长期沉淀的能力资产，而不是散落的 prompt 或脚本

让 skill 的创建、修改、评估、检索形成闭环

让 skill 的管理方式更接近笔记软件，而不是纯 CLI

让个人用户在完全本地、可控的环境里维护自己的 skill library

4. 目标用户
核心用户

长期使用 Claude Code / Codex / OpenClaw / 其他 agent 工具的人

已经开始积累自己的 skill，但管理混乱的人

有本地工作流、希望长期维护个人能力资产的人

不满足于“安装 skill”，而想自己创建、调优、复用的人

典型用户画像

个人 AI 重度使用者
已经有几十到上百个 skill，找不到、管不住、版本混乱

方法论型创作者 / 产品经理 / 顾问
希望把自己的经验、流程、套路封装成 skill

本地优先用户
不希望自己的 skill 完全依赖外部平台或公有市场

5. 产品定位
Skill Notebook 不是

不是公域 skill marketplace

不是团队协作平台

不是纯 CLI 工具

不是单纯 prompt 收藏夹

Skill Notebook 是

一个 本地 skill library

一个 skill 编辑器

一个 skill 版本管理器

一个 skill 检索与评估工作台

它是介于 笔记软件 + IDE + 轻量 Git 客户端 之间的产品。

6. 设计原则
6.1 本地优先

所有核心能力默认在本地完成，skill 资产归用户自己所有。

6.2 低压力维护

用户不应该因为管理 skill 而增加太多额外心智负担。

6.3 结构化 + 可编辑

skill 既是结构化对象，也是文本对象。
因此必须同时支持：

结构化表单编辑

Markdown / 文件级编辑

6.4 评估先于发布

skill 不是“写完就算完成”，而应经过最小评估。

6.5 检索驱动复用

skill 多了以后，首要问题不是“再创建一个”，而是“先找到已有的”。

7. 核心功能（V1）

V1 只做四件事：

Skill 版本管理

Skill 自然语言创建

Skill Eval 评估

Skill 检索

它们形成一个闭环：

Find → Create → Evaluate → Version

7.1 Skill 版本管理
目标

让 skill 变成可演化资产，而不是静态文本。

要解决的问题

改了一版以后，不知道哪里变了

某次优化把 skill 改坏了，回不去

不同版本的 prompt / examples / tools 配置难以追踪

评估结果无法和版本绑定

V1 功能
基础能力

新建版本快照

自动保存草稿

查看历史版本列表

版本备注

查看两个版本的 diff

回滚到指定版本

每个版本至少记录

version id

保存时间

修改摘要

skill 内容快照

metadata 快照

eval 结果快照

边界

不做多人协作 merge

不做远程同步冲突处理

不做 GitHub PR 级别的复杂版本流

7.3 Skill Eval 评估
目标

用结构化检查和评估建议，替代“凭直觉觉得这个 skill 好像可以”。

背景参考

42plugin 公开上线了 42eval，并明确把它定义为“用数据代替直觉，衡量你的 AI 技能值不值得用”，其公开描述包括“断言测试 + 盲测对比，量化每个技能的实际贡献”。

要解决的问题

# Skill Notebook 开发规约（V1）

## 项目目标
构建一个面向个人本地使用的 Skill 管理与编辑工具，支持：
1. Skill 版本管理
2. Skill 自然语言创建（调用 skill-create）
3. Skill Eval 评估
4. Skill 检索

产品形态应接近“笔记软件 + IDE + 轻量 Git 客户端”。

---

## 设计原则
- 本地优先，不依赖云端账号系统
- 低压力维护，避免复杂协作系统
- 三栏布局：Library / Editor / Inspector
- Skill 既是结构化对象，也是文本对象
- 所有核心操作都应可追溯、可回退

---

## MVP 范围
### P0
- 工作区管理（本地目录）
- Skill 列表浏览
- 搜索（关键词）
- Skill 新建 / 编辑
- 结构化编辑 + Markdown 编辑
- 自然语言创建草稿
- Eval 基础检查
- 版本保存与历史列表
- 版本恢复

### P1
- Diff 对比
- 语义检索
- 派生新 skill
- Eval 历史记录

### P2
- 本地 Git 集成
- 批量评估
- 导入导出 ZIP
- 执行测试面板

---

## 技术建议
### 前端
- Next.js / React
- 本地桌面优先可考虑 Tauri 或 Electron
- UI 尽量简洁，偏笔记软件风格
- 支持深色模式

### 数据层
- 本地 SQLite 或轻量 JSON/文件系统索引
- Skill 原始内容保存在本地文件夹
- 元数据与索引可额外存储
- 版本快照独立保存

### 检索
- V1 先做关键词检索
- 检索字段：name / description / tags / examples / references
- 后续可加 embedding 语义检索

### 版本管理
- 每次“保存为新版本”生成快照
- 版本对象至少包含：
  - skill 内容
  - metadata
  - eval 结果
  - timestamp
  - note

### 自然语言创建
- 提供单独 service 层调用 skill-create
- 输出结果为可编辑草稿
- 不直接覆盖已有 skill，必须显式保存

### Eval
- 输出包含：
  - overall_status
  - completeness_score
  - clarity_score
  - executability_score
  - suggestions[]

一个面向个人本地使用的 Skill 管理与编辑工具。

## 3. 产品愿景
让 skill 像笔记一样被沉淀，像代码一样被版本化，像工具一样被复用。

## 4. 背景
现有公开 skill 平台证明了 skill 的创建、搜索、安装、评估是成立的产品逻辑。
但对于个人用户来说，真正的痛点并不是“市场里有没有 skill”，而是：
- skill 资产是否属于自己
- skill 是否可以长期维护
- skill 是否能在本地持续积累
- skill 是否会因为外部平台变化而丢失

Skill Notebook 的目标不是做一个新的 marketplace，而是做一个个人本地版 Skill Hub 管理编辑器。

## 5. 目标用户
- 长期使用 Agent / CLI / Skills 的个人用户
- 有几十到上百个 skill，管理混乱的人
- 希望把方法论、工作流、经验沉淀成 skill 的创作者
- 偏好本地优先、长期可控的用户

## 6. 核心问题
1. skill 多了以后难以检索和复用
2. skill 的修改缺乏版本追踪
3. 从想法到 skill 草稿的创建成本较高
4. skill 是否清晰、可用，缺乏基础评估手段

## 7. 产品目标
Skill Notebook V1 解决四个问题：
1. Skill 版本管理
2. Skill 自然语言创建
3. Skill Eval 评估
4. Skill 检索

## 8. 核心闭环
Find → Create → Evaluate → Version

## 9. 功能定义

### 9.1 Skill 版本管理
#### 目标
将 skill 视为可演化资产，而非静态文本。

#### V1 支持
- 保存版本快照
- 自动保存草稿
- 历史版本列表
- 版本备注
- diff 对比
- 恢复旧版本

---

### 9.2 Skill 自然语言创建
#### 目标
通过调用 skill-create，把自然语言需求转成 skill 草稿。

#### V1 支持
- 输入自然语言描述
- 调用 skill-create
- 生成 skill 初稿
- 用户继续编辑
- 保存为新 skill 或新版本

#### 原则
自然语言创建只负责“起草”，不负责“自动定稿”。

---

### 9.3 Skill Eval
#### 目标
用结构化评估替代纯直觉判断。

#### V1 维度
- 完整性
- 清晰度
- 可执行性
- 示例质量

#### 输出
- 总体结论
- 分项评分
- 优化建议

---

### 9.4 Skill 检索
#### 目标
让用户优先找到已有 skill，再决定是否创建新的。

#### V1 支持
- 关键词检索
- 搜索 name / description / tags / examples / references
- 列表结果展示
- 打开 / 派生 / 编辑

1. 核心对象不是单文件，而是技能包

Skill Notebook 管理的最小对象，不是一个 SKILL.md 文件，而是一个技能包。

一个技能包至少包含：

SKILL.md

prompts

examples

references

scripts

test assets

eval report

version metadata

也就是说，Skill Notebook 的界面不应该把 skill 当成“一篇笔记”，而应该像笔记软件管理一个“笔记条目”，同时像文件管理器一样展开这个条目下面的一组文件。

这会直接影响信息架构：

左侧看到的是 技能包列表，
中间编辑的是 技能包主视图，
右侧查看的是 元信息、版本、测评、预览。

2. 预览和测试是内建能力，不是附属功能

你这个判断也很对。

因为 skill 不是纯文本资产，它最终是要被执行的。
所以一个 skill 包创建出来后，用户最关心的不只是“内容对不对”，而是：

它长什么样

它能不能跑

它在典型场景下是不是合理

所以 Skill Notebook 必须同时具备两种工作模式：

笔记本模式

适合：

浏览技能包

编辑文档和说明

看结构、看引用、看 examples

预览 skill 内容

命令行 / 测试模式

适合：

执行 skill

跑测试

查看日志

做快速验证

所以不是“二选一”，而是：

Notebook 负责维护与理解，CLI 负责执行与验证。

产品上最合适的做法不是把 CLI 隐藏掉，而是给它一个清楚的位置，比如：

右下角测试面板

底部 console drawer

“Run in CLI” 按钮

“Preview / Test” 标签页

3. 创建与测评是独立功能，但默认串联

这个定义非常重要。

创建

创建的目标是：
把自然语言需求转成一个可编辑的技能包草稿。

测评

测评的目标是：
判断这个技能包当前是否足够清晰、完整、可执行。

它们不是同一件事，所以产品上必须是两个独立模块。
但从用户流程上，它们应该被默认串起来。

也就是：

首次创建完成后，自动触发一次测评。

这里的关键不是“自动跑”，而是你说的那句：

要有用户感知

这点很重要。不能静默完成。

正确做法应该是：

创建完成后，界面明确进入“首次测评中”

用户看到进度和状态变化

测评完成后，给出一个清晰结果页

明确告诉用户：这个 skill 当前处于什么状态，下一步建议是什么

这样用户会把“创建 skill”理解成一个完整动作，而不是生成一坨文本就结束。

4. 改完 skill 后，要主动提醒测评

这也很对，因为 skill 的价值不在编辑，而在可用。

所以只要发生了关键修改，系统就应该进入一种“待重新验证”的状态。

建议定义一个状态机制：

状态

草稿中

待测评

已通过测评

已过期（修改后待重新测评）

逻辑是：

新建 skill → 草稿中

创建完成 → 自动首次测评

测评完成 → 已通过 / 待优化

用户改动关键内容后 → 变成“待重新测评”

这里的“关键内容”包括：

SKILL.md 主体

prompts

examples

scripts

tools 配置

而不是任何小改动都强制打断用户。

产品提示语可以很克制：

你修改了 skill 的核心内容，建议重新运行一次 Eval。

不要做成强制弹窗打断，但要持续可见，比如：

顶部黄色提示条

右侧 Eval 面板红点

版本状态从“已验证”切到“待验证”

5. 版本保存应以“测评后版本”为主

这个点一落下去，产品逻辑一下就稳了。

不是每次保存都算一个正式版本。
正式版本应该和测评绑定。

更准确地说：

草稿保存

随时发生

用于防丢和继续编辑

不计入正式版本历史

正式版本保存

以测评完成为触发点

保存 skill 包快照

绑定测评结果

写入版本历史

这样版本才有意义。
不然一堆无效版本会把历史弄脏。

所以我建议把产品规则定成：

正式版本 = 一次测评完成后的技能包快照

这很像代码世界里的 release，而不是普通 save。

6. 每个技能包最多保留 10 个正式版本

这个限制非常好，因为它迫使产品设计更克制。

我建议这样理解：

不限制草稿自动保存数量或按最近清理

只限制“正式版本历史”最多 10 个

超过后默认滚动淘汰最旧版本

但在淘汰前提醒一次用户，或者允许“钉住版本”

这样你既控制了复杂度，也不会让版本系统无限膨胀。

建议机制

每个技能包：

正式版本最多 10 个

可标记 1~2 个“重要版本”

被标记的重要版本不优先淘汰

其他版本按时间滚动替换

这会比纯粹机械删除更好。

# Skill Notebook PRD

## 1. 产品名称
Skill Notebook

## 2. 一句话定义
一个面向个人本地使用的 Skill 管理与编辑工具。

## 3. 产品愿景
让 skill 像笔记一样被沉淀，像代码一样被版本化，像工具一样被复用。

## 4. 产品背景

过去一段时间，公开 skill 平台已经证明了几件事情：
- skill 可以被自然语言创建
- skill 可以被搜索和复用
- skill 需要评估，而不是只靠直觉判断
- skill 的价值不只是“安装”，而是长期维护与演化

但对于个人用户来说，真正的核心问题并不是“市场里有没有 skill”，而是：

1. 我的 skill 资产是不是属于我自己
2. 我的 skill 能否长期在本地沉淀和维护
3. 我的 skill 修改后是否可追踪、可回退
4. 我能否低压力地持续积累 skill，而不是把它们丢在公共平台或零散文件夹里

Skill Notebook 的起点不是 marketplace，而是：

> 一个完全属于个人、本地优先、可长期维护的 Skill 工作台。

## 5. 核心问题

Skill Notebook 主要解决四类问题：

### 5.1 资产归属问题
skill 不能完全托管在外部平台上。  
用户需要一个可控的、本地优先的能力资产容器。

### 5.2 维护成本问题
skill 不是一次性文本，而是会不断演化的能力对象：
- prompt 会改
- examples 会补
- references 会增删
- scripts 会调整
- 评估结果会变化

### 5.3 创建门槛问题
用户通常先有一个需求或意图，再有一个 skill。  
从“我想做一个 skill”到“我写出一个完整可用的 skill 包”之间存在明显门槛。

### 5.4 复用与判断问题
skill 多了以后，核心不是“再写一个”，而是：
- 先找到已有的 skill
- 判断它当前是否可用
- 在已有基础上继续迭代

## 6. 产品目标

Skill Notebook V1 只做四件事：

1. Skill 的版本管理
2. Skill 的自然语言创建
3. Skill Eval 测评
4. Skill 检索

这四件事形成一个闭环：

> Find → Create → Evaluate → Version

## 7. 目标用户

### 7.1 核心用户
- 长期使用 Claude Code / Codex / OpenClaw / 自建 Agent 的个人用户
- 已经开始积累自己的 skill，但管理混乱的人
- 希望把方法论、流程、经验沉淀成 skill 的创作者
- 偏好本地优先、可控、长期维护的人

### 7.2 典型用户画像
#### A. 个人 AI 重度使用者
有几十到上百个 skill，散落在不同文件夹或平台中，缺少检索与版本化管理。

#### B. 方法论型创作者
希望把文章、工作流、经验、套路转成 skill，并持续优化。

#### C. 本地优先用户
不接受 skill 资产完全依赖公有平台，希望本地长期沉淀。

## 8. 产品定位

### 8.1 Skill Notebook 不是
- 不是公域 Skill Marketplace
- 不是团队协作平台
- 不是纯 CLI 工具
- 不是单纯 prompt 收藏夹
- 不是 workflow 编排器
- 不是 skills bundle 管理平台（至少不是 V1）

### 8.2 Skill Notebook 是
- 一个本地 skill library
- 一个 skill package 编辑器
- 一个 skill package 评估器
- 一个 skill package 版本管理器
- 一个 skill package 检索工作台

## 9. 核心设计原则

### 9.1 本地优先
所有核心能力默认在本地完成。skill 资产归用户自己所有。

### 9.2 技能包优先
系统管理的最小对象是“技能包（skill package）”，不是单个 `SKILL.md` 文件。

### 9.3 低压力维护
用户不应该为了“管理 skill”而被迫学习复杂系统。

### 9.4 结构化 + 文本双编辑
skill 既是结构化对象，也是文本对象。产品必须同时支持：
- 结构化编辑
- Markdown / 文件级编辑

### 9.5 测评先于正式版本
不是每次保存都形成正式版本。  
正式版本必须和测评绑定。

### 9.6 检索优先于重复创建
skill 多了以后，首要问题不是“新建”，而是“先找到”。

## 10. 核心对象定义

## 10.1 技能包（Skill Package）
Skill Notebook 管理的最小对象是技能包，而不是单个 skill 文件。

一个技能包至少由以下内容组成：
- `SKILL.md`
- `prompts/`
- `examples/`
- `references/`
- `scripts/`
- `tests/`（可选）
- `preview assets`（可选）
- `eval report`
- `version metadata`

### 10.2 技能套包（未来保留）
多个技能包未来可以再组织形成“技能套包（skill bundle）”。

但这不是 V1 范围。V1 不支持：
- 套包创建
- 套包编排
- 套包依赖管理
- 套包级检索
- 套包级测评

V1 只在数据结构层面保留未来扩展可能。

# 11.1 Skill 检索

## 目标
让用户先找到已有的 skill package，再决定是否创建新的。

## V1 范围
检索和列表阶段只展示三类信息：
- 名称（name）

# 11.2 Skill 自然语言创建

## 目标
通过调用 `skill-create`，把自然语言需求转成一个可编辑的技能包草稿。

## 输入
用户用自然语言描述：
- 这个 skill 要干什么
- 输入是什么
- 输出是什么
- 适用场景是什么
- 是否有参考材料

## 执行
调用 `skill-create`

## 输出
生成一个技能包草稿，至少包含：
- 名称
- 一句话描述
- `SKILL.md` 初稿
- examples 初稿
- prompts 初稿（可选）
- 初始 metadata

## 原则
自然语言创建 = 自动起草  
不是自动定稿。

---

# 11.3 Skill Eval 测评

## 目标
用结构化测评替代纯直觉判断。

## V1 测评维度
### A. 完整性
检查是否具备基础结构：
- `SKILL.md`
- name
- description
- examples
- metadata
- references（可选）

### B. 清晰度
检查：
- 任务目标是否清楚
- 输入是否明确
- 输出是否明确
- 边界是否明确

### C. 可执行性
检查：
- prompts 是否存在
- scripts / tools 配置是否合理
- examples 是否与 skill 目标一致
- skill package 是否具备最小可运行条件

### D. 建议输出
给出 3~5 条具体建议，例如：
- examples 太少
- 描述过泛
- 输出约定不稳定
- 引用材料不足
- 脚本与说明不一致

## 输出结果
测评完成后至少给出：
- 总体结论（可用 / 可优化 / 问题较多）
- 分项评分
- 建议列表

# 11.4 Skill 版本管理

## 目标
将 skill package 视为可演化资产，而不是一次性文本。

## 两类保存
### A. 草稿保存
- 自动保存
- 用于防丢和继续编辑
- 不计入正式版本历史

### B. 正式版本保存
- 以测评完成为前提
- 保存技能包快照
- 绑定测评结果
- 计入版本历史

## 正式版本规则
- 每个技能包最多保留 10 个正式版本
- 超过 10 个后，滚动淘汰最旧的未固定版本
- 允许标记少量“重要版本”（V1 可选）

## 版本至少记录
- 版本号
- 保存时间
- 备注
- 技能包快照
- 测评结果快照

---

# 11.5 预览与测试

## 目标
skill package 不是纯文本对象，必须可预览、可测试。

## V1 支持
### 预览
- 预览技能包结构
- 预览 `SKILL.md`
- 预览 examples
- 预览 references
- 预览最终导出内容

### 测试
- 提供测试入口
- 支持通过命令行执行测试
- 查看测试输出与日志

## 产品原则
Notebook 和 CLI 都需要：
- Notebook 负责理解、维护、浏览、组织
- CLI 负责执行、测试、验证

CLI 不是替代品，而是 Notebook 的执行层。

## 12. 关键交互规则

### 12.1 首次创建后自动测评
用户通过自然语言创建技能包后，系统自动触发一次首次测评。

必须有明确用户感知：
- 创建成功提示
- 进入“首次测评中”
- 显示测评进度 / 状态
- 输出测评结果
- 提示是否保存为正式版本

### 12.2 修改后主动提醒重新测评
当用户修改技能包的核心内容时，系统应将其状态标记为：
- 待重新测评

核心内容包括：
- `SKILL.md`
- prompts
- examples
- scripts
- tools 配置

系统应以非强打断方式提醒：
- 顶部提示条
- Eval 区域红点
- 状态切换

### 12.3 测评后保存正式版本
正式版本应绑定一次明确的测评结果。  
没有测评的保存，默认只算草稿保存。

## 13. 主工作流

→ 打开技能包

→ 编辑  
→ 测评  
→ 保存新版本

# Skill Notebook 技术规约（Rust 优先版）

## 1. 技术目标

基于 Rust 为核心能力层，构建一个本地优先的桌面应用，支持：

1. 技能包管理
2. 本地索引与检索
3. 调用 `skill-create`
4. 调用 Eval 引擎
5. 正式版本管理（最多 10 个）
6. 预览与 CLI 测试

产品形态应优先适配：
- macOS（第一优先）
- 兼容 Windows / Linux（第二阶段考虑）

---

## 2. 技术选型建议

## 2.1 桌面框架
### 推荐
**Tauri 2 + Rust Core + React/TypeScript 前端**

### 原因
- Rust 负责本地系统能力、文件系统、版本逻辑、索引、CLI 调用
- 前端负责三栏 UI、编辑器、状态管理
- Tauri 比 Electron 更轻，适合本地工具
- 本地文件访问、命令调用、窗口管理都比较自然

---

## 2.2 前端
### 推荐
- React
- TypeScript
- Vite（由 Tauri 模板带）
- Zustand（轻状态管理）
- TanStack Query（可选）
- CodeMirror 6 或 Monaco Editor（编辑器）
- shadcn/ui + Tailwind（界面）

### 原则
前端不承担业务真相，只承担：
- 展示
- 状态交互
- 命令调用入口

业务真相应尽量放在 Rust 层。

---

## 2.3 后端核心（Rust）
### 推荐 crates
- `tauri`
- `serde`, `serde_json`
- `tokio`
- `sqlx` 或 `rusqlite`
- `chrono`
- `uuid`
- `walkdir`
- `ignore`
- `anyhow`
- `thiserror`
- `diff` / `similar`
- `notify`（本地文件变更监听）
- `regex`

### 检索
V1 推荐优先使用：
- **SQLite + FTS5**
或者
- 纯 SQLite 普通索引 + Rust 内存过滤（更简单）

由于 V1 检索字段只有：
- name
- description
- tags

V1 可不引入 Tantivy。  
等到要做 examples / semantic search 再升级。

---

## 2.4 数据存储
### 推荐
- 本地文件系统存技能包原始内容
- SQLite 存索引、元数据、版本记录、评估结果

### 原因
- 技能包天然适合以文件夹形式存在
- SQLite 适合做本地元数据查询和版本追踪
- 文件系统 + SQLite 的组合最稳

负责：
- 页面渲染
- 三栏布局

负责：

# Skill Notebook PRD

> Skill Notebook V1 is macOS-only.

## 1. 产品名称
Skill Notebook

## 2. 一句话定义
一个面向个人、本地优先、仅支持 macOS 的 Skill 管理与编辑工具。

## 3. 产品愿景
让 skill 像笔记一样被沉淀，像代码一样被版本化，像工具一样被复用。

## 4. 平台范围
Skill Notebook V1 是一款仅面向 macOS 的本地桌面应用。

默认运行环境：
- macOS
- 本地文件系统

## 5. 产品背景

过去一段时间，skill 生态已经证明了几件事情：

1. skill 可以被自然语言创建  
2. skill 可以被搜索和复用  
3. skill 需要评估，而不是只靠直觉判断  
4. skill 的价值不只是“安装”，而是长期维护与演化  

但对于个人用户来说，真正的核心问题并不是“市场里有没有 skill”，而是：

- 我的 skill 资产是不是属于我自己
- 我的 skill 能否长期在本地沉淀和维护
- 我的 skill 修改后是否可追踪、可回退
- 我能否低压力地持续积累 skill，而不是把它们散落在公共平台或零散文件夹里

Skill Notebook 的起点不是 marketplace，而是：

> 一个完全属于个人、本地优先、可长期维护的 Skill 工作台。

## 6. 核心问题

Skill Notebook 主要解决四类问题：

### 6.1 资产归属问题
skill 不能完全托管在外部平台上。  
用户需要一个可控的、本地优先的能力资产容器。

### 6.2 维护成本问题
skill 不是一次性文本，而是会不断演化的能力对象：
- prompt 会改
- examples 会补
- references 会增删
- scripts 会调整
- 评估结果会变化

### 6.3 创建门槛问题
用户通常先有一个需求或意图，再有一个 skill。  
从“我想做一个 skill”到“我写出一个完整可用的 skill 包”之间存在明显门槛。

### 6.4 复用与判断问题
skill 多了以后，核心不是“再写一个”，而是：
- 先找到已有的 skill
- 判断它当前是否可用
- 在已有基础上继续迭代

## 7. 产品目标

Skill Notebook V1 只做四件事：

1. Skill 的版本管理
2. Skill 的自然语言创建
3. Skill Eval 测评
4. Skill 检索

这四件事形成一个闭环：

> Find → Create → Evaluate → Version

## 8. 目标用户

- 偏好本地优先、可控、长期维护的人

### 8.2 典型用户画像

#### B. 方法论型创作者

#### C. 本地优先用户

## 10. 核心设计原则

### 10.1 本地优先
所有核心能力默认在本地完成。skill 资产归用户自己所有。

### 10.2 技能包优先
系统管理的最小对象是“技能包（skill package）”，不是单个 `SKILL.md` 文件。

### 10.3 低压力维护
用户不应该为了“管理 skill”而被迫学习复杂系统。

### 10.4 结构化 + 文本双编辑
skill 既是结构化对象，也是文本对象。产品必须同时支持：
- 结构化编辑
- Markdown / 文件级编辑

### 10.5 测评先于正式版本
不是每次保存都形成正式版本。  
正式版本必须和测评绑定。

### 10.6 检索优先于重复创建
skill 多了以后，首要问题不是“新建”，而是“先找到”。

### 10.7 macOS 原生体验优先
V1 不考虑跨平台一致性，不为 Windows / Linux 做兼容抽象。  
所有交互优先服从 macOS 的使用习惯，包括：
- 文件选择与导入
- 快捷键
- 菜单结构
- 通知与窗口行为
- 本地 shell 调用方式

## 11. 核心对象定义

- `SKILL.md`
- `prompts/`
- `examples/`
- `references/`
- `scripts/`
- `tests/`（可选）
- `preview assets`（可选）
- `eval report`
- `version metadata`

### 11.2 技能套包（未来保留）
多个技能包未来可以再组织形成“技能套包（skill bundle）”。

但这不是 V1 范围。V1 不支持：
- 套包创建
- 套包编排
- 套包依赖管理
- 套包级检索
- 套包级测评

V1 只在数据结构层面保留未来扩展可能。

### 12.2 Skill 自然语言创建

通过调用 `skill-create`，把自然语言需求转成一个可编辑的技能包草稿。

#### 执行
调用 `skill-create`

#### 输出

### 12.3 Skill Eval 测评

#### 目标
用结构化测评替代纯直觉判断。

#### V1 测评维度

##### A. 完整性
检查是否具备基础结构：
- `SKILL.md`
- name
- description
- examples
- metadata
- references（可选）

##### B. 清晰度
检查：
- 任务目标是否清楚
- 输入是否明确
- 输出是否明确
- 边界是否明确

##### C. 可执行性
检查：
- prompts 是否存在
- scripts / tools 配置是否合理
- examples 是否与 skill 目标一致
- skill package 是否具备最小可运行条件

##### D. 建议输出
给出 3~5 条具体建议，例如：
- examples 太少
- 描述过泛
- 输出约定不稳定
- 引用材料不足
- 脚本与说明不一致

#### 输出结果
测评完成后至少给出：
- 总体结论（可用 / 可优化 / 问题较多）
- 分项评分
- 建议列表

### 12.4 Skill 版本管理

#### 目标
将 skill package 视为可演化资产，而不是一次性文本。

#### 两类保存

##### A. 草稿保存
- 自动保存
- 用于防丢和继续编辑
- 不计入正式版本历史

##### B. 正式版本保存
- 以测评完成为前提
- 保存技能包快照
- 绑定测评结果
- 计入版本历史

#### 正式版本规则
- 每个技能包最多保留 10 个正式版本
- 超过 10 个后，滚动淘汰最旧的未固定版本
- 允许标记少量“重要版本”（V1 可选）

#### 版本至少记录
- 版本号
- 保存时间
- 备注
- 技能包快照
- 测评结果快照

### 12.5 预览与测试

#### 目标
skill package 不是纯文本对象，必须可预览、可测试。

#### V1 支持

##### 预览
- 预览技能包结构
- 预览 `SKILL.md`
- 预览 examples
- 预览 references
- 预览最终导出内容

##### 测试
- 提供测试入口
- 支持通过 macOS 本地 shell（zsh / bash）执行测试
- 查看测试输出与日志

#### 产品原则
Notebook 和 CLI 都需要：
- Notebook 负责理解、维护、浏览、组织
- CLI 负责执行、测试、验证

CLI 不是替代品，而是 Notebook 的执行层。  
V1 默认假设用户运行环境为 macOS 本地 shell，不处理跨平台 shell 差异。

## 13. 关键交互规则

### 13.1 首次创建后自动测评
用户通过自然语言创建技能包后，系统自动触发一次首次测评。

必须有明确用户感知：
- 创建成功提示
- 进入“首次测评中”
- 显示测评进度 / 状态
- 输出测评结果
- 提示是否保存为正式版本

当用户修改技能包的核心内容时，系统应将其状态标记为：
- 待重新测评

核心内容包括：
- `SKILL.md`
- prompts
- examples
- scripts
- tools 配置

系统应以非强打断方式提醒：
- 顶部提示条
- Eval 区域红点
- 状态切换

### 13.3 测评后保存正式版本
正式版本应绑定一次明确的测评结果。  
没有测评的保存，默认只算草稿保存。

- 读取 `notebook.json`
- 拷贝快照
- 读取 `SKILL.md`
- 列出 `examples/`, `prompts/`

这一层很重要，因为 Skill Notebook 的核心对象是“文件夹里的技能包”。

---

## 4. `services/`
负责真正的业务逻辑。

### 例如
#### `skill_create_service.rs`
- 调 `skill-create`
- 解析结果
- 落盘成 draft package
- 触发首次 Eval

#### `eval_service.rs`
- 收集 package 文件
- 做结构化检查
- 生成 `EvalReport`
- 更新 package 状态

#### `version_service.rs`
- 保存正式版本
- 裁剪到最多 10 个
- 恢复版本

---

## 5. `commands/`
只暴露给前端，尽量薄。

比如 `package.rs` 里只写：

- `package_list`
- `package_get`
- `package_update`
- `package_create_from_nl`

不要把复杂业务塞 command。
