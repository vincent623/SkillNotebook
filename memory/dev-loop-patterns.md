# Dev Loop Patterns

## 2026-04-14

### Spec Alignment Review Should Separate Four States

- When reviewing progress against PRD or TECH_SPEC, classify findings into four buckets: aligned, explicitly incomplete, spec drift, and logic inconsistency.
- This prevents us from treating every missing feature as a bug, while still surfacing the cases where implementation semantics have diverged from the intended product.

### Integration Name Matching Is Not Enough

- If the spec says a feature is powered by one concrete integration, but the code uses a different runtime path, treat that as semantic drift rather than cosmetic substitution.
- In this project, "natural-language drafting via skill-create" is not equivalent to "Claude CLI with template fallback" unless the spec is updated to say so.

### Reconcile Drift By Making The Bridge Explicit

- If multiple generators exist (`skill-create`, Claude CLI, template), make the selection order explicit in code and surface it in Settings + docs.
- Add a small auto-mode test matrix so future refactors do not reintroduce drift.

### Workspace Must Become A First-Class Runtime Context Early

- If workspace is a core product object, bootstrap, create, eval, search, and recent/open flows must all share the same current-workspace source of truth.
- A default-workspace-only architecture can look complete in a single demo environment while silently blocking multi-workspace behavior later.

### External CLI Bridges Need Operational Guardrails Immediately

- As soon as a feature depends on an external CLI, add timeout, fallback, and focused regression tests in the same iteration.
- Without those guardrails, a bridge feature can appear successful in happy-path tests while introducing hang risks into the main product loop.

### Preserve Human-Facing Generator Output During Slug Normalization

- Slug deduplication should only rewrite machine identifiers.
- Human-facing names generated by the draft engine should be preserved unless they are empty or invalid, otherwise uniqueness handling leaks infrastructure concerns into product copy.

### Placeholder Surfaces Should Be Counted, Not Just Noted

- Commands or modules marked "planned", "placeholder", or pass-through should be tracked as explicit incompleteness in loop reviews.
- This helps distinguish a scaffolded surface from a real shipped capability, especially around versions, snapshots, SQLite, and test execution.

### Snapshots Should Not Overwrite Notebook Metadata

- Copy package content into snapshots while excluding `notebook.json`, so future restore flows can avoid rolling back formal-version history and eval records.

### Automation Needs An Explicit Queue File

- If we want a watchdog or recurring automation to keep shipping work, give it a single prioritized queue file instead of forcing it to infer next steps from prose metrics alone.
- Metrics explain the state of the project; the queue should answer "what do we do next?" with checkable items.
